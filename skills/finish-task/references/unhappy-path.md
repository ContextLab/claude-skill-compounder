# Unhappy path

The failure-to-route table. When any phase fails, comes back empty, or prints something the body
did not lead you to expect, find its row here before you act: each one names what the failure
voids and which phase to run forward from. Each row names what the failure voids, where to
resume, and — where there is one — the measurement behind that route.

## Where to re-run from

Go back to the phase in the "Re-run" column and run *forward from there*, not from where you
stopped:

| What happened | Void | Re-run from |
|-|-|-|
| Cold reviewer found something and you fixed it | the sweep, the prose audit, the record | Phase 1 |
| The review packet is 0 bytes, or the suite passes with your change absent | everything | **Read Phase 1's `BASE IS HEAD` line before you conclude anything.** If it printed, the sha you retyped *is* `HEAD` — pick the commit below your work, retype, rebuild the packet. Only if it did not print is the work absent from the tree: `git stash list`, `git log --oneline -5`. Never stash the unit of work |
| The dispatch itself left files in the tree | the sweep | Phase 1 step 2 — remove or ignore them, then stage by name. Its writes continue after it returns, so read the state again just before staging |
| You committed what the dispatch left behind (`git add -A`) | the sweep, and the review packet if it was dominated by them | Phase 1 — `git rm -r --cached <path>`, ignore it, commit that; re-dispatch the review if that packet was mostly state |
| Cold reviewer could not be dispatched | nothing | Phase 3, with the gap written into the record and stated in your reply |
| The sweep failed | the sweep, everything after it | Phase 1 — the fix is unreviewed code, and Phase 1 is where it gets committed |
| The sweep failed on a tree `git diff` says is byte-identical to a state you watched go green | nothing yet — **do not go looking for a defect in the code** | Somebody's break-and-revert left a build artifact compiled from source that is no longer on disk — a cold reviewer probing your suite, `claim-provenance`'s test trap. Measured 9 trials in 12: `git diff --stat` empty, suite still red. `stale-artifact-check` owns this; its canary is what tells you, and its Phase 3 is what fixes it |
| Phase 3's canary was absent | the sweep — it is not evidence | `stale-artifact-check` Phase 2 and 3. Come back when it is observed |
| Phase 3's canary was **observed** and the sweep is red anyway, on a tree `git diff` says is unchanged | the sweep | The stale artifact is in a file you did not canary, and the canary cannot see it. Measured: `canary OBSERVED`, `exit=1`, `AssertionError: 11 != 10`, `git diff --stat` empty. `stale-artifact-check` Phase 3 clears the pipeline; re-run the sweep before you go looking for a defect |
| Phase 3's removal check printed `YOUR CANARY IS STILL HERE` and the path it lists is a `CANARY-…` **file** | nothing | Phase 3 — that file is what the canary *created*, and **removing the canary means removing it too**. `rm -f ./CANARY-<your token>`, by exact name, never a `CANARY-*` glob, then run that skill's check again. Measured on the default canary form with the source line already gone: the check printed `./CANARY-1788251186-7b0c0e67` and exit 1 with nothing in `stale-artifact-check` that deletes it, so the default path had no exit at all; after the `rm -f` the same check printed `CLEAN: your canary is gone` |
| Phase 3's removal check printed `YOUR CANARY IS STILL HERE` on a source you have already cleaned | nothing — and **not** a failed removal | `stale-artifact-check`, which owns every cause of it; this skill enumerates none, because two rounds of review each found a cause the previous round's list did not cover. Follow it until its Phase 4 check prints `CLEAN`, then sweep. Never edit the source a second time — it is already clean. A run whose removal was never confirmed does not reach Phase 6 |
| The canary is still absent once `stale-artifact-check` reports the artifact is current | nothing | Nothing in the suite covers your change. Say so in the record, in those words; do not record a green as coverage |
| `claim-provenance` changed prose | the sweep | Commit it in Phase 4, then Phase 3. No other phase will commit it |
| `claim-provenance` changed code, a test, or an assertion | the sweep, the prose audit | Phase 1 |
| The sweep passed and you then edited anything at all | the sweep | Phase 3. The **one** expected post-sweep edit is the record, and Phase 5's confirming sweep is what covers it — that is the only edit this skill answers with a confirming sweep rather than a re-run from Phase 3 |
| The confirming sweep came back red | nothing yet — the record broke the suite by existing, and no code moved | Phase 5 step 2 — fix what the failure names, commit it **by name**, run the confirming sweep again. Measured: a record at `<docs>/notes/rec.md`, under a suite asserting `<docs>/index.md` lists every file under `<docs>/`, gave `AssertionError: 'notes/rec.md' not found`, `exit=1`; the index entry made it `exit=0`. Two repairs without a green means the path is fighting the sweep — move the record to the commit body |
| `cp -a` into the scratch tree printed `Permission denied` on `.git/objects/…` and exited 1 | nothing | Phase 3 — you copied into a destination that already holds a copy, and git's objects are read-only. **The stale copy is still there and `ls` on it looks correct**, which is the danger. `mktemp -d /tmp/finish-REPLACE/scratch-XXXXXX` and copy into that; never `cp -a` twice into one destination |
| `git status --porcelain -uall` lists a tracked file as ` M` or ` D` at a phase boundary | nothing — the sweep still covers it | Commit it by name. Do **not** re-sweep; the tree did not move, only the index and `HEAD`. Measured: a Phase 4 prose correction left uncommitted reached neither the pushed branch nor the merged main, while the record claimed it had been made |
| `git status --porcelain -uall` lists a `??` path you cannot place | nothing | The commit rule's third case, and the only one of the three that leaves the path alone: **do not commit it and do not delete it**, and say in the record that it is in the tree and not in the branch. "Prefer deleting" in Phase 1 step 2 is the *second* case — tooling state you **can** place — and does not reach this row |
| Phase 6's published list holds a file you cannot name as part of the work | the sweep | Phase 1 — un-track and ignore it, commit that, then forward from Phase 3 |
| You reached Phase 6, or pushed, with the record uncommitted | nothing — but the record reaches no branch | Phase 5 — `git add <record path>` and commit it. Measured: uncommitted, it survived neither the push route nor the merge-and-delete route |
| `git add <record path>` printed `The following paths are ignored` and exited 1 | nothing | Phase 5 — `git add -f <record path>`, once, on the record only. Do **not** re-run the plain `git add`; it will refuse again, and the `git commit` after it says `nothing to commit, working tree clean` while the record is still missing. Phase 0 step 3's check is what catches this before anything is written |
| A block failed with `No such file or directory` on `/tmp/finish-REPLACE/…` | nothing | You missed a retype. Substitute what `mktemp -d` printed in Phase 0 step 4. Do **not** `mkdir` the placeholder: the failure is the guard, and the directory it would create is the one every run shares |
| A cold reviewer re-reported a finding you had dispositioned as deliberately not fixed | nothing | Nothing — this is expected, since each reviewer is new. It does not count as a round's new finding. Two independent reviewers raising it is evidence the disposition is wrong; re-examine it, and record the count either way |
| `git diff <base> HEAD --name-only` lists a file that is not part of this unit of work | nothing yet — **do not build a packet from it** | Phase 0 step 2 — the base is too far back. Pick a **newer** sha, further up `git log --oneline -20`, and read the list again. Measured on a branch cut from `develop` in a clone that also carries `origin/main`: a base resolved against `origin/main` listed `d1.txt d2.txt d3.txt work.txt`, three of them a colleague's, where the hand-named base listed `work.txt` alone (`naming-the-base.md`) . **If the newest sha in the log is `HEAD` itself and your work is not committed yet, `HEAD` is the correct base and this row does not apply** — going one commit further back is what produces the colleague's file, and "pick a newer sha" then walks you back to `HEAD`. That loop is the round-4 deadlock; see the `BASE IS HEAD` rows below |
| `git diff <base> HEAD --name-only` is missing a file you know is part of this unit of work | nothing | **Before** the Phase 1 commit this is expected — your work is uncommitted, so it is not in the list by construction; go on to Phase 1. **After** it, the base is inside your own work: pick an **older** sha, further down the log, and read the list again |
| The list is empty **before** Phase 1, or `git log --oneline -20` shows the work already committed and pushed | nothing | Phase 1 — commit, then read the list again. A finish on already-published work has no ref marking its lower edge, which is exactly why the base is named by hand rather than derived; measured, the hand-named sha gave a one-file packet where the whole-history one gave four |
| The cold reviewer returned nothing: a 0-byte file, or an answer with no findings and no sentence saying it found none | the round | Phase 2 — re-dispatch. Measured: a real dispatch exited **0** with a **0-byte** review file. An empty answer is not "found nothing"; a second empty answer means no cold reviewer was available, and that goes in the record in those words |
| The project's record convention points at a path the sweep reads | nothing | Phase 0 — prefer a path outside the trees the suite walks, or the commit body. That is a guess and not a guarantee: what a suite reads cannot be enumerated from outside it, which is why the confirming sweep is owed on every route. What a swept path adds is that it can come back **red because of the record**, which Phase 5 step 2 repairs. Re-quoting the record into the newest sweep is the move that never terminates and has no fixed point |
| The record exists only as session prose, or only in a PR description you have not opened yet | nothing — but the record reaches no branch | Phase 5 — a file on the branch, or a commit body. Measured against a real bare remote: on the merge-locally route `git log --all -p \| grep -ci record` printed `0`, and two of the three integration options never open a PR at all |
| `finishing-a-development-branch` reported failing tests | the sweep | Phase 1 — your Phase 3 sweep and its Step 1 disagree, and that disagreement is itself a finding |
| The review loop hit its three-round cap, or the early-stop trigger fired | the round budget, and nothing else | **Phase 7** — fix every finding that has a reproduced failure scenario, sweep, then pick **Parked**, **Withdrawn** or **Re-scoped** and write it as the record's first sentence. The cap is not grounds for leaving a reproduced defect unfixed, and "stopped, findings open, nothing decided" is not an end state. Never Phase 6 |
| The confirming sweep is **still** red after two repairs *and* after the record moved to the commit body | the run — nothing is publishable | **Phase 7**, by its second entrance. The record is out of the tree, so the suite is red for something that is not the record; measured, the residue was the two repairs themselves — an index entry added in repair 1 still naming the file repair 3 deleted. Fix what Phase 7 step 1 names, sweep, and stop in a disposition. Never a third pass through Phase 5 step 2 |
| Phase 0 step 2 printed `BASE IS HEAD` and none of your work is committed yet | nothing — **this is the expected reading, not an error** | Phase 0, unchanged: keep that sha, go on with an empty packet, and let Phase 1's commit make it provable. Before the commit the newest commit that is not your work usually *is* `HEAD`. Measured, on a branch whose parent commit held a colleague's `.ci/config.yml`: obeying "pick the commit below your work" gave a packet of `.ci/config.yml`, the too-far-back row then said "pick a **newer** sha", and the only newer sha is `HEAD` — no sha satisfies both, which is why the Phase 0 reading no longer demands a change |
| Phase 1 printed `BASE IS HEAD`, after the commit | the packet, and the review round it would have fed | Phase 1 — **here it really is an error**: the commit above moved `HEAD` past your base, so a base equal to `HEAD` can only be a sha you retyped from the wrong line. Pick the commit below your work and retype. Both counts being 0 is this, not lost work |
| Phase 0 step 2 printed `ON THE INTEGRATION TARGET` | nothing yet — but Phase 6's handover and all three of Phase 7's dispositions | Phase 0 step 2. **Uncommitted work:** `git switch -c <a branch name you choose>` carries it across, and that is the whole repair. **Already committed on that branch:** this skill cannot move it back — it issues no `reset` and no history rewrite — so say so in your reply, write "the work is already on `<target>`" into the record, and read Phase 7's dispositions against that, since "Parked on `main`, unmerged" would be false. Measured: work committed on `main` passes Phase 0's repo check, its detached-HEAD check, and all four Phase 6 checks, and `superpowers:finishing-a-development-branch` then offers "merge back to `main`" for a branch that already is `main` |
| A review finding you accepted is a fix to a path Phase 0 step 1's sentence does not name | nothing | Phase 0 step 1 — **amend the sentence** to cover the tooling that finding touched, say so in the record, and judge the file list against the amended sentence. Without the amendment no sha satisfies both readings: measured on a branch whose round-2 fix touched `run_tests.sh`, `base=8301c86` listed `calc.py run_tests.sh test_mul.py` (extra path → "pick a newer sha"), `base=065b433` listed `run_tests.sh test_mul.py` (a work file missing → "pick an older sha"), and `HEAD` is Phase 1's `BASE IS HEAD` error. A path you would **not** amend the sentence to cover is not a base problem at all — pick a newer sha, or if it sits inside one of your own commits, leave it and record it as in the branch and not part of the work |
| Phase 4 changed prose only, and the canary you placed in the changed `.md` came back `ABSENT` | nothing | Phase 5 — record, in those words, that nothing in the suite covers the prose change, and do **not** re-place the canary at module scope in a source file. Measured: a README-only correction with the canary moved into `src/shapes.py` came back `OBSERVED`, certifying a file the change never touched. What the prose re-sweep proves is the narrower thing — that the corrected prose did not turn the suite red |
| Phase 0 step 2 printed `DETACHED HEAD` | nothing yet — but every phase after Phase 5 | Phase 0 step 2, before anything else: `git switch -c <a branch name you choose>`, which keeps `HEAD`'s commits and puts a branch on them, then carry on. Measured on git 2.50.1: a detached `HEAD` passes **all four** of Phase 6's checks, and then `git branch --show-current` prints nothing and `git rev-parse --abbrev-ref '@{u}'` answers `fatal: HEAD does not point to a branch` — there is nothing to hand `superpowers:finishing-a-development-branch`, and Phase 7's Parked and Withdrawn both need "its own branch". Checking out away at that point orphans every commit to the reflog. If you cannot name a branch to make, this skill declines exactly as the non-git case does |
| A block printed `PLACEHOLDER MESSAGE`, `STILL THE EXAMPLE PATH`, `A SHIPPED LITERAL SURVIVED` or `MISSED THE RETYPE: name the branch` | nothing | The phase you are in — a commit message, a record path and a branch name are **free literals**: every command accepts one, so no check can reject the value and a `case` on the literal is the only guard there can be. Two of the four **refuse** (Phase 1's message, Phase 0's target), because a placeholder there enters the review packet or a guess picks the wrong branch; two **name it and go on** (Phase 0 step 3, Phase 5), because those blocks must still create the record's directory and land the record. Measured before any of them existed: `git commit -m "..."` exited **0** with `git log -1 --format=%s` reading back `...`, and `git commit --allow-empty -m "record: ..."` did the same |
| Phase 5's block printed `add exit=128` and did not commit | nothing | Phase 5 — `[ "$a" = 0 ]` is what stopped it, and it stopped it on purpose: with the add failed, a bare `git commit` would have committed whatever else was staged under the record's message. Write the record at the path you declared, or fix the path, then run the block again |
| Phase 1 step 2 printed `MISSED THE RETYPE: '<d>' is not a directory` | nothing | Phase 1 — substitute what Phase 0 step 4's `mktemp -d` printed and run the block again. **Do not `mkdir` the placeholder.** Until 2026-09-01 this branch read `round 1 -- no dispatch yet, nothing to subtract` and exited **0**, because its guard was `[ -f /tmp/finish-REPLACE/post-dispatch.txt ]` and an unretyped placeholder can never satisfy it: the reassurance was printed on round 2 of a real review loop, silently skipping the step measured at 98.7% contamination |
| Phase 1 step 2 printed `round 1: no snapshot pair in '<d>' yet` and `<d>` *is* the directory `mktemp -d` gave you | nothing | Nothing — this is the true round-1 reading, and it is only reachable once the line above it did not fire. Go on to step 3 |
| Phase 1 step 4 printed `NOTHING IS STAGED` | the commit that was about to happen | Phase 1 step 3 — you staged nothing, so the `grep` for machine-local paths on the next line searched an empty diff and its `no machine-local absolute paths` reassurance is about nothing. Stage by name, then read the block again |
| Phase 0 step 3 printed `NOTHING WAS EXAMINED (exit 128)` | the run | Phase 0 step 2 — `git check-ignore` answers 128 only outside a work tree, so this is the non-git decline arriving one step late |
| Phase 0 step 2 printed `NOT A GIT REPOSITORY` | the run | Nothing here — this skill declines the non-git case at Phase 0 step 2 and that is the whole route. Walked in a real directory with no `.git`, six of the eight phases are impossible and three of the commands exit **0** while doing nothing. `git init` and commit, or invoke `stale-artifact-check`, `claim-provenance` and `superpowers:requesting-code-review` directly |
| `git log --oneline -20` answered `your current branch 'main' does not have any commits yet` | nothing | Phase 0 — commit first, then start again at step 2. `HEAD` does not resolve, so there is neither a base nor a packet |
| You are looking at several `finish-*` directories under `$TMPDIR` and want to tidy up | nothing here | **Nothing in this skill deletes one, and neither should you as part of a finish.** Yours is the one whose absolute path Phase 5 wrote into the record. A cleanup written on a shared prefix has destroyed live evidence twice, and four rounds of cold review could not produce an ownership check this document does not itself satisfy (`the-scratch-directory.md`). Deleting one is your own command, outside this skill, where `destructive-op-preflight` fires on its own trigger |
